AURORA · Assessment guide

What Happens at Each Step

A practical guide to the ten-stage SaaS resilience workflow, showing where the language model drafts or interprets, where fixed framework rules apply, and where human review is essential.

Reflects the current implementation. The Level descriptions and score mapping are provisional; they have not been empirically calibrated.

Read This First

A language model (LLM) produces language and structured proposals from prompts and the information supplied to it. A prompt can tell it to follow rules, but a prompt is not proof that its answer is true or compliant. The application enforces only the checks implemented in code. A human must verify source accuracy and approve the assessment.

LLM proposal

The model generates, summarizes, classifies or interprets. Unless a stage says otherwise, the output is a hypothesis to review, not verified fact.

Framework / code

Fixed catalogues, validation, formulas, thresholds and status rules. These are repeatable, but the rubric itself can still be provisional.

Human decision

A person checks evidence, chooses Manual or AI suggestions, confirms or edits ratings and approves each workflow gate.

4 · RateLevel, Position and review

Important: “LLM follows the framework” is a goal, not an automatic guarantee. Structured JSON, prompts and evidence checks reduce errors. They do not give the model a live, verified knowledge base or independently prove that a statement is true.

Key limitation The current API sends prompts to the configured model; it does not give the model a browser/search tool. “Research” prompts can draw on model knowledge and supplied text. Any returned claims, quotations, dates and URLs need source-level verification.

The Ten Stages

01

Company Discovery

Establish the company profile that later recommendations and narratives use as context.

LLM proposal What it does

When configured, it drafts the company name, description, industry, size category and a small set of public-fact evidence items. It is asked to use well-known public information and not fabricate data or URLs.

Code behavior What is enforced

The response is parsed as JSON and stored. Evidence starts as proposed, not accepted. There is no independent source fetch or factual cross-check in this step.

Assumptions / risks Where judgment enters

The model may rely on remembered information, infer an industry or size, or return a plausible but incorrect source detail. Its prompt classifies small as under $500M revenue, medium as $500M–$5B, and large as over $5B; these are prompt conventions, not verified framework rules. Missing model fields can default to Technology or medium.

Reviewer action What to check

Correct the profile. Open original sources, compare every material claim and date, and accept or reject each evidence item. Do not treat a returned URL as verified: current code treats a non-null URL as resolved without fetching it.

No maturity score is assigned here. When the LLM is unavailable or fails, the app can use mock profiles/evidence; those must be replaced with real research before evaluation.

02

Scenario Context

Describe four possible operating futures in terms relevant to the company.

LLM proposal What it does

Drafts narrative text for the four predefined combinations of AI implementation depth and macroeconomic disruption, using the company name, industry and size provided.

Framework What is fixed

The four scenario keys and their broad premises are defined by AURORA. The model is asked to return text for those keys; the application does not calculate probabilities for the futures.

Assumptions What is not evidence

The scenario conditions are intentional “what if” premises. Company-specific impacts in the narrative are model-generated possibilities, not observed facts, forecasts or likelihood estimates. This step is not grounded in accepted company evidence.

Reviewer action What to check

Keep scenario premises distinct from current-state claims. Edit unsupported company-specific assertions and approve the narratives before they are used in stress testing.

Fallback mode uses fixed narrative templates marked as mock. A mock narrative is not an LLM result or company research.

03

Dimension Screening

Decide which of AURORA’s 15 dimensions receive deeper sub-dimension assessment.

LLM recommendation What it does

Recommends relevance and deep-assessment selections from the company description, industry and size. It is prompted to include all 15 dimensions and usually select 10–13 for deeper review.

Framework What is fixed

The dimension catalogue and SaaS materiality descriptions are fixed. If the model is unavailable, default selections come from the hard-coded SaaS materiality table. The user can edit the selection and rationale.

Assumptions What may vary

The model’s “materiality” ranking is qualitative and not calibrated. It may infer importance from generic industry knowledge. The default size notes do not automatically change the scoring thresholds.

Reviewer action What to check

Review omitted dimensions carefully; select dimensions based on business exposure, product criticality and regulation, not the model’s confidence. Confirm coverage requirements before approving.

Coverage interaction: the composite now uses every qualifying dimension; no minimum dimension count is imposed. If only a few dimensions are assessed, a composite is still calculated but represents limited coverage, which the report displays beside the score.

04

Evidence Plan

Decide what records will be sought for each selected dimension or sub-dimension.

Human-authored What happens

The user creates, edits and saves the evidence plan. The current implementation has no LLM evidence-plan generation call.

Code behavior What is enforced

The API checks that the submitted plan is an array, then saves it. It does not verify that each target is measurable, sufficient, or aligned with the frozen reporting period.

Assumptions Common gap

A broad source target such as “annual report” does not guarantee the report contains the measure, covers the assessment period, or supports a particular criterion.

Reviewer action What to specify

For each target, name the required metric, definition, reporting period, acceptable source, sub-dimension, and evidence that would count as a successful test or failure.

05

Evidence Gathering

Collect records, associate them with sub-dimensions, and have a person decide whether each may be used.

LLM research proposal What it does

When configured, the model is prompted to produce claims, values, quotations, source names, URLs, publication dates and sub-dimension assignments for plan targets. It is told to prefer primary sources, avoid fabrication and skip unsupported targets.

Code behavior What is enforced

Returned evidence is stored as proposed; it does not count as accepted until reviewed. Without the LLM, a mock research path can produce illustrative records. Mock evidence must never be treated as company evidence.

Assumptions What is not verified

The research function sends a prompt to the model; it does not itself browse the web or fetch each cited document. A quotation, extracted number, publisher, URL or publication date may be wrong. A URL being present is not proof it resolves to that document.

Reviewer action What to check

Open the original source; confirm exact text, value, unit, measurement date, scope, calculation method and sub-dimension. Accept only evidence that actually supports the claim. Reject mock or unverifiable records.

06

Sub-Dimension Ratings

Review accepted evidence and assign each selected sub-dimension a Level, Position and score.

Manual entry What happens

Choose a Level and Position, link accepted evidence, add a brief rationale and reviewer name, then confirm. If evidence does not support a rating, leave the sub-dimension unscored.

AI suggestions What it does

When enabled and accepted non-mock evidence exists, the LLM suggests Level, Position, confidence, rationale and evidence IDs. If it cannot support a rating, it returns no score and the reviewer can enter one manually.

Framework calculation What code checks

The application checks that Level and Position form a valid pair and that referenced evidence is accepted and assigned to this sub-dimension. It then calculates the numeric score using the band minimum and Position offset. No eight-item checklist or exact-date gate is required in this simplified flow.

Where judgment remains What code cannot know

The LLM may misinterpret evidence or make an unsupported inference. A valid Level/Position response does not prove a rating is correct. Reviewers should verify source meaning, scope and reporting period; the rubric has not been empirically calibrated.

Human confirmation What to do

Accept or edit each AI suggestion, or enter a manual rating. Ratings remain unscored until a named reviewer confirms them. Stage approval requires every selected sub-dimension to have a current reviewed rating or an explicit unscored result.

Sub-dimension score = Level band minimum + Position points

Low +3 · Mid +12 · High +21. The rubric’s Level/Position result is converted by code, not selected as a free-form number by the LLM.

For example, Level 3 + Mid becomes 51 + 12 = 63/100. Position is a reviewer judgment within the selected Level. Changing a saved rating invalidates later approvals so dependent calculations can be refreshed.

07

Dimension and Composite Scoring

Turn reviewed sub-dimension numbers into dimension and overall scores. This stage is deterministic.

Code only What it calculates

Each dimension averages its eligible numeric sub-dimension scores equally. R1 requires at least 2 of 3. Its Level is looked up from the resulting band; maturity levels are not averaged and rounded. The composite equally averages every qualifying dimension. Zero qualifying dimensions means no average can be calculated.

Additional checks What they mean

The app reports evidence coverage and an R3 sensitivity comparison between the reported composite and a Full-evidence-only mean. Review readiness requires a calculable composite and no pending or stale reviews; there is no minimum qualifying-dimension count.

Assumptions Policy, not AI

Equal weighting, R1 and R3 are chosen scoring rules, not LLM conclusions or empirically validated predictive rules. Averages can rise when weaker items are missing; sensitivity checks cannot eliminate all missing-data bias. With no overall minimum, very sparse coverage can still produce a composite.

Reviewer action What to check

Inspect partial coverage and critical weaknesses beside any mean. Dimension overrides are not allowed; revise the underlying Level/Position ratings instead. When comparing companies, confirm their evidence covers comparable periods.

08

Scenario Stress Test

Explore how current dimension capability could change if a defined future scenario occurred.

LLM interpretation What it does

If a dimension has a base Level and relevant evidence exists, the model proposes a scenario Level, direction, confidence and rationale. It is given the scenario’s fixed premise and accepted dimension evidence.

Code / mock fallback What is enforced

Code bounds the returned Level to 1–4 and recalculates direction from the returned Level versus base. If the model is unavailable or errors, a hard-coded scenario-by-dimension shift map supplies a heuristic result; results are marked mock. No base Level means no scenario score.

Assumptions What it is not

A scenario Level is a judgment under a hypothetical premise, not a forecast, probability, simulation or newly measured capability. Model reasoning can extrapolate beyond evidence. The fallback shift map encodes fixed assumptions such as “budget pressure weakens liquidity.”

Reviewer action What to check

Check each change against both scenario conditions and evidence. Challenge generic or unsupported changes. Record a reason for edits and approve the scenario result before relying on it.

09

Resilience Gaps

Translate base and scenario results into Strong, Conditional or Exposed classifications and leadership-level gap descriptions.

Code only What it does

Fixed rules classify dimensions from base and available scenario Levels. Templates produce gap text, implications, recommendations and early-warning indicators. This stage does not call the LLM.

Framework rules Classification

Strong requires base Level at least 3 and all available scenario Levels at least 3; Conditional means some are below 3; Exposed includes base below 3 or all scenarios below 3. A low base score also generates a base gap when no weakening scenario is recorded.

Assumptions / caveat What to watch

Template language is generalized. Current classification uses the scenario results that exist; it does not require a complete set of four before classifying. Missing scenarios can therefore make the output look more complete than it is. “No gap generated” does not mean no risk exists.

Reviewer action What to check

Check that all four scenarios were assessed and approved. Ensure each gap links to relevant evidence and that classifications reflect missing-data limitations. Recommendations are leadership prompts, not company-specific implementation plans.

10

Final Assessment and Report

Present the assembled assessment, source trail, readiness checks and sub-dimension explanations.

Code / presentation What happens

The dashboard renders saved profiles, direct Level/Position ratings, formula-derived dimensions, scenario results, classifications, alerts, gaps, evidence and audit trail. Readiness blockers and export content are computed from saved data.

No new LLM judgment

Opening or printing the final report does not ask a new model to rescore, reclassify or validate the assessment. It displays prior outputs and computed rules.

Interpretation

The scores are framework-based capability indicators, not probabilities of resilience or proof of future outcomes. This provisional rubric has not yet been calibrated against disruption and recovery data.

Final responsibility

Confirm sources, periods, rubric version, review identities, coverage, mock markers, endpoint exceptions and scenario completeness before presenting conclusions.

How the Framework Converts Findings to Scores

The scoring flow is intentionally simple: accepted evidence → optional AI suggestion → reviewer accepts, edits or enters Level + Position → application calculates the score. A separate Criterion Policy freeze is not required for new ratings.

What remains deterministic

The LLM does not choose the final numeric score or perform dimension/composite arithmetic. The reviewer chooses or confirms Level and Position; code maps the pair to a score. The application retains a small guardrail that a scored rating links to accepted evidence and has a named reviewer. It does not require exact-quote matching, an observation-date window or eight separate criterion findings.

Reviewer Checklist

  • Confirm the company profile, size classification, critical-service profile and reporting dates from independent information.
  • Open sources yourself. Verify document identity, URL, exact excerpt, publication date, measurement period, unit and sub-dimension.
  • Keep “unknown” when evidence is missing or ambiguous. Do not turn nondisclosure into a failure or a success.
  • For Stage 6, confirm the AI suggestion or manual Level/Position, rationale and linked accepted evidence. Leave unsupported ratings unscored.
  • Distinguish scored data from proposed, mock, pending, stale or endpoint-override records.
  • Check all 15 dimensions, sub-dimension coverage, the four critical dimensions, all four scenarios, and the reasons behind exclusions.
  • Record reviewer identity and rationale. Keep scenario assumptions visibly separate from observed company facts.
  • Describe the result as a provisional framework-based assessment, not as a validated resilience probability, credit rating or investment recommendation.

Workflow approvals are checkpoints for human review. Navigating backward to read a prior page does not itself make an LLM output verified; editing inputs can invalidate later approvals.
